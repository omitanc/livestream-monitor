# プロジェクト引き継ぎメモ

更新日: 2026-09-28

## 確定した要望

- 自分のYouTube Liveを、配信者側ではなく視聴者側から監視する。
- 最初はYouTube Live専用。将来のニコ生・X・Instagram Live・Twitch対応は今回の範囲外。
- Electron＋TypeScriptで専用アプリ内にYouTubeを表示する。両基盤の比較試作は行わず、この構成で必要な動作を検証しながら実装する。
- macOSとWindowsの両方で使用できるようにする。
- 長時間の監視でも軽量に動作し、CPU・メモリ・ディスク使用量を適切に管理する。キャッシュやログを無制限に増やさない。
- アプリのGUIから更新操作を行い、新版の取得・適用・再起動まで進められるようにする。配布先や更新ライブラリは未確定。
- 配信映像には秒単位のデジタル時計を入れられる。時計の更新停止と視聴遅延を検出する。
- 映像本体のフリーズ、指定領域の黒画面・特定色がn分続く状態も検出する。時計が動いていてもカメラだけ止まる場合がある。
- YouTubeの視聴側がライブ位置を失うことがあるため、設定可能なn分間隔のページ再読み込みと、異常時のライブ位置への復帰を検討する。
- 異常時には監視PCで警報音を鳴らし、外出中にも届く緊急通知を行う。
- 監視PCやアプリの停止は、自前サーバーを立てず既存の外部API/サービスで検知したい。

## 検討中の設計（未確定）

- アプリ基盤はElectron＋TypeScriptを採用（2026-09-28）。GUIはReact。YouTubeを表示するWebContentsViewとローカルGUIを分離し、Node integration無効、context isolation・sandbox有効にする。Macを初期検証環境とし、Windowsは後続の実機検証対象。
- 送出PCと監視PCの時刻を合わせ、時計表示をOCRなどで読む。時刻差から遅延を測り、通常の配信遅延を基準として閾値を設定する。OCR不能は別状態。
- 本編のフリーズ判定から時計・コメント・操作UIを除外する。黒画面判定は指定領域で行う。再生停止・配信終了・広告・観測不能を区別する。
- 自動復旧は「ライブ位置へ戻る → ページ再読み込み → プレーヤーまたはアプリ再起動」を候補とし、回数を制限する。リロードは障害の継続時間を無条件にリセットしない。復旧後は時計と映像で確認する。
- Healthchecks.ioで監視処理の定期ping欠落を検出できる。PC停止、アプリ停止、回線断のどれかは外部から区別できない。監視処理の稼働と配信の正常性を別チェックにする候補。
- PushoverのEmergency通知は確認まで再通知できる。ローカル警報音とスマホ通知を分け、消音・確認・テスト再生・復旧通知を設ける。Healthchecks.ioとPushoverの連携も候補。
- 設定値、通知先、APIの認証情報は機密として扱い、Gitに記録しない。

## 軽量動作・キャッシュ管理の設計候補

- YouTube再生と解析の負荷を分けて計測する。アプリ本体だけでなく、WebView・動画デコード・GPU等の関連プロセスを含めて評価する。
- 映像取得・解析は常時全フレーム処理を避け、まず毎秒1〜2回程度を仮置きする。時計は切り出した領域をOCRし、本編の差分・黒画面・特定色は縮小画像や指定領域で判定する。周期は検出精度を見て調整する。
- 解析処理は同時実行数と待ち行列に上限を設け、遅れた場合は古いフレームを捨てる。取得時刻と処理の遅れを管理し、観測不足を正常扱いしない。
- 解析画像は必要最小限をメモリに保持し、通常は連続保存・再エンコードを行わない。解析ワーカーを再利用し、リロード時にタイマー・リスナー・古い画像を解放する。
- HTTPキャッシュ、ログ、障害時画像、更新ファイルにそれぞれ容量・保存期間・削除タイミングの方針を設ける。ブラウザ管理領域の上限制御と計測可否は基盤ごとに検証する。
- Cookie等のログイン情報と削除可能なキャッシュを区別する。リロードのたびに全キャッシュを削除せず、監視への影響が少ないタイミングで整理する。GUIに使用量表示とキャッシュ削除操作を設ける候補。
- 最小化時は不要なUI更新を減らしつつ、再生・映像取得・判定・heartbeatを継続できるか検証する。解析頻度を下げてもYouTube再生自体の負荷は残るため、再生画質と時計の可読性も評価する。
- Tauriとの比較試作は行わない。Electronで解決しにくい問題が判明した場合に再検討する。配布サイズと実行時負荷は分け、軽さを未計測のまま断定しない。

## GUI更新の設計候補

- GitHubの omitanc/livestream-monitor を利用し、GitHub Releases＋electron-updaterを実装の出発点とする。署名・実際の更新配布は未設定。専用の更新サーバーは当初不要な構成を目指す。
- アプリに「更新を確認」「更新して再起動」を用意し、バージョン・変更内容・進捗・失敗理由を表示する。最新の安定版からOS・CPUアーキテクチャに合う成果物を選ぶ。
- 監視中に無断で再起動しない。適用時の短い監視中断を明示し、設定・監視対象を引き継いで再起動後に監視を再開する。再生・映像取得・判定の復帰まで確認する。
- 更新中の外部死活監視は有限の猶予期間を検討し、復帰失敗を無期限に隠さない。ダウンロード失敗時は現行版を維持し、適用失敗時の復旧手順も検証する。自動ロールバックの可否は未確定。
- HTTPSと署名検証を前提とする。更新用の署名とOSのコード署名は別に扱い、macOSのDeveloper ID署名・公証、Windowsのコード署名とインストール権限を検討する。署名・配布の費用やアカウント準備は未確定。
- 公開Releasesなら利用側のGitHubトークンを不要にする構成を優先する。ソース公開は別判断とし、必要なら配布専用リポジトリを分ける。非公開配布の認証方式は別途設計し、秘密トークンをアプリに埋め込まない。
- 他の候補は静的HTTPS配信や更新配信サービス。配布規模・非公開配布・段階的配信などの必要性が出てから比較し、初期構成は小さく保つ。

## 技術検証と受け入れ条件

- 配信映像の時計停止、映像本体だけの停止、黒画面、意図的な静止画、視聴遅延、広告、配信終了、ログイン切れを識別する。
- ページ再読み込み、ライブ位置への復帰、アプリ再起動で解析が継続する。
- 最小化、PCロック、スリープ、ネットワーク断、監視アプリ終了時の挙動をMac/Windows実機で確認する。
- 異常検出からPC警報音とスマホ通知まで通しで試し、復旧通知と通知の重複抑制も確認する。
- 閾値やn分間隔は初期値を仮置きし、実配信の遅延・画面内容を見て調整する。
- 両OSで通常表示・最小化・繰り返しリロードを比較し、CPU・メモリ・GPU・ディスク増加量を記録する。長時間試験の時間と負荷上限は対象PCでの短時間計測後に決める。
- 実際にインストールした旧版から新版へのGUI更新を両OSで検証する。設定保持、監視再開、通信断、署名不一致、空き容量不足、再起動失敗を確認する。
